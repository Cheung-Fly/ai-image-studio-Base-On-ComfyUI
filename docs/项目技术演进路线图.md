## 阶段 0：Docker 全链路容器化（已完成）

- **目标**：Redis / API / Worker 三个服务容器化，日常开发测试全部在 Docker 上进行。
- **关键决策**：
  - ComfyUI 留在宿主机（GPU 直通），Worker 容器通过 `host.docker.internal` 回调。
  - 构建上下文提升到项目根目录（修掉 `COPY ../workflows` 越界问题）。
  - API 代码通过 volume 挂载（`./backend/app:/app/app`）+ `--reload` 实现热更新。
- **已踩坑记录**（学习者务必记住）：
  1. `docker compose` 必须在含 `docker-compose.yml` 的项目根目录执行。
  2. 国内拉 `python:3.13-slim` 需配镜像加速器（`registry-mirrors`）。
  3. `registry-mirrors` 必须放在 daemon.json 的**顶层**，不能塞进 `builder` 里。
  4. JSON 逗号必须是英文半角 `,`，中文逗号 `，` 会报错。
- **日常命令**：`docker compose up -d --build`（启动）/ `docker compose logs -f api`（看日志）/ `docker compose restart worker`（重启 worker）。

## 阶段 1：本地模型底座（llama.cpp + 多模态 + RAG）

### 1.1 llama.cpp 本地 LLM（✅ 子步骤1已完成 2026-09-24）

**已完成内容**：

- 模型选型：**Qwen3-8B**（2025.04 发布），量化 **Q4_K_M**（5.03GB），8GB 显存可跑，约 8 token/s。
- 运行方式：宿主机直接跑 `llama-server.exe`（本机已装 `D:\llama\llama-b11105-bin-win-cuda-13.4-x64`），**未容器化**（保留 GPU 加速，规避 Windows GPU 直通麻烦）。
- 后端接入：`docker-compose.yml` 的 api 服务加 3 个环境变量 → 对话走本地模型。

**启动命令**：

```powershell
cd D:\llama\llama-b11105-bin-win-cuda-13.4-x64
.\llama-server.exe -m .\models\Qwen3-8B-Q4_K_M.gguf --host 0.0.0.0 --port 8080 --n-gpu-layers 45 --ctx-size 4096
```

**关键环境变量**（api 服务）：

- `LLAMA_BASE_URL=http://host.docker.internal:8080/v1`（容器访问宿主机，`/v1` 是 OpenAI 兼容路径）
- `LLAMA_API_KEY=not-needed`（假 key，骗过后端「无 key 走占位回复」的判断）
- `DEFAULT_LLM_PROVIDER=llama`

**踩坑记录**：

1. 模型文件**不要打进镜像**，放宿主机目录（`D:\llama\...\models`）即可，llama-server 直接读。
2. llama-server 是**前台进程**，关窗口即停，需保持窗口开启。
3. 中文在 PowerShell 控制台显示乱码是**编码问题**（PowerShell 默认 GBK），非模型问题；浏览器/后端 UTF-8 正常。
4. 容器访问宿主机端口用 `host.docker.internal`（不是 127.0.0.1）。
5. `--ctx-size 4096` 限制上下文省显存；8GB 显存跑 8B 需错峰（与 ComfyUI 不同时满负荷）。

### 1.1 待办（后续）

- 可选：llama 容器化（需评估 Windows GPU 直通，当前保留宿主机方式）。

### 1.2 多模态理解模型（✅ 已完成 2026-09-24）

**已完成内容**：

- 模型选型：**Qwen3-VL-8B**（2025.05 发布），Q4_K_M 主模型（5.0GB）+ mmproj-F16 视觉投影（1.3GB），8GB 显存可跑。
- **用 VL 模型「替换」了纯文本 Qwen3-8B**（一个模型通吃对话 + 看图，省显存）。
- 启动命令（加 `--mmproj`）：  
  `.\llama-server.exe -m .\models\Qwen3VL-8B-Instruct-Q4_K_M.gguf --mmproj .\models\mmproj-Qwen3VL-8B-Instruct-F16.gguf --host 0.0.0.0 --port 8080 --n-gpu-layers 40 --ctx-size 4096`
- 后端改动：`schemas.py` 的 `ChatRequest` 加 `image_base64` 字段；`llm_client.py` 的 `_build_messages` 支持 OpenAI 多模态 content 数组（image_url + text）；`chat.py` 透传。
- 前端改动：`index.html` 对话区加「传图」按钮 + FileReader 转 base64 + 预览/移除。

**踩坑记录**：

1. mmproj 必须用 F16（不要量化），否则视觉精度损失。
2. 图片走 base64 data URL（`data:image/xxx;base64,...`），前端 `FileReader.readAsDataURL` 生成，后端直接拼进 `image_url.url`。
3. VL 模型 `prompt_tokens` 很大（图片被编码成视觉 token），首次编码较慢（约 100 秒/图）属正常。

### 1.3 RAG（检索增强生成）（✅ 最小闭环完成 2026-09-24）

**已完成内容（阶段 3a 最小闭环，宿主机脚本验证）**：

- 技术选型：**ChromaDB**（向量库，PersistentClient 持久化）+ **bge-small-zh-v1.5**（embedding，CPU 跑）+ 本地 Qwen3-VL（生成）。
- 脚本 `rag_demo.py`（项目根目录）实现完整链路：读 `docs/*.md` + README + start_local → 切片（400 字/段，重叠 50）→ 向量化 → 存 ChromaDB → 检索 Top-5 → 拼 prompt → 调 llama 生成带出处回答。
- 验证通过：问「What APIs does this project provide?」→ 检索命中 API接口文档/README → 正确列出 API。

**关键决策**：

- embedding 用 **CPU 跑**（bge-small-zh 仅 100MB），不挤占 8GB 显存（显存已被 Qwen3-VL 占）。
- 依赖装独立 venv `rag-venv`（`chromadb` + `sentence-transformers==3.2.0`，锁定版本避开 torchcodec CUDA 报错）。
- HF 下载走 `HF_ENDPOINT=https://hf-mirror.com` 国内镜像。

**踩坑记录**：

1. 清华 PyPI 源找不到 chromadb（`from versions: none`）→ 换阿里云源。
2. `sentence-transformers` 新版依赖 torchcodec 缺 CUDA 库报错 → 锁 `==3.2.0`。
3. **零宽字符坑**：`if __name__ == "__main__"` 里混入不可见字符 U+200B，导致入口判断永远 False、脚本无输出 → 改用 `main()` 函数手动调用绕开。
4. 中文问题在 PowerShell 命令行传参易乱码 → 先用英文问题验证。

**3b 集成进后端（✅ 已完成 2026-09-24）**：

- 目标：`/api/chat` 加 `use_rag` 开关，网页对话即可做知识库问答（固定 md 做知识库）。
- 改动：
  - `requirements.txt` 加 `chromadb>=0.5.0` + `sentence-transformers==3.2.0`
  - `config.py` 加 RAG 配置（rag_docs_dir / rag_chroma_dir / rag_hf_cache_dir / rag_embed_model / rag_top_k）
  - 新增 `app/services/rag.py`（ensure_index / retrieve / build_rag_prompt，懒加载 embedding + chroma 持久化）
  - `schemas.py` ChatRequest 加 `use_rag`；`chat.py` use_rag 分支（检索 → 拼 prompt → llm）
  - `Dockerfile` pip 阿里云源 + `COPY docs /app/knowledge`（固定文档进镜像）
  - 前端 `index.html` 对话区加「知识库」checkbox，勾选后请求带 `use_rag=true`
- 验证通过：命令行 `use_rag=true` 问「What APIs...」→ 基于项目文档正确列出 API。
- 踩坑：
  1. `.dockerignore` 原先排除了 `docs`，导致 `COPY docs` 失败 → 改为只排除 `docs/*.html`。
  2. pip 装 torch 极慢（阿里云源下载大包，build 耗时约 78 分钟）——后续可考虑用 CPU 版 torch 或拆分镜像层优化。

**3b-2 知识库动态管理（✅ 已完成 2026-09-24）**：

- 目标：前端点「+」上传 md 加入知识库、点「删除」移除，搭配后端固定 md（固定文档不可删）。
- 改动：
  - `config.py` 加 `rag_dynamic_dir=/data/rag_docs`（动态文档目录，经 ./data:/data 挂载持久化）
  - `rag.py` 新增 `add_document` / `remove_document` / `list_documents`；`ensure_index` 改索引固定+动态双目录；动态文档 source 加 `custom:` 前缀防重名冲突
  - 新增 `api/rag_docs.py`：`GET /api/rag/docs`（列表）、`POST /api/rag/docs`（上传 md，multipart）、`DELETE /api/rag/docs/{filename}`（删除）
  - `main.py` 注册 `rag_docs` 路由
  - 前端 `index.html`：对话区加「管理」按钮 + 知识库面板（文档列表 / 上传 / 删除，固定文档标「内置」不可删）
- 验证通过：命令行测「列出 5 个固定文档 → 上传 rag_test.md（chunks=1）→ 删除 → 回到 5 个」全链路 OK。
- 踩坑：前端 `apiFetch` 默认 `Content-Type: application/json` 会破坏 multipart 上传 → 上传改用原生 `fetch` 手动带 `Authorization` 头。

## 阶段 3：智能体与质量保障

### 3.1 多 Agent 调度

- 选型决策：自研轻量编排 + 复用 Celery/Redis（不引入 LangGraph 等重框架）。
- 把「Agent」建模成「角色 + 工具 + 记忆」单元，编排器经队列调度。
- Agent 的工具调用落到 Celery worker 执行。

**✅ 起步场景已完成（2026-09-24）**：

- 场景：**一句话生图流水线**（提示词优化 → 生图 → 审图），固定流程编排。
- 实现：`services/agents.py`（PromptAgent / GenerateAgent / ReviewAgent + `run_pipeline` 编排器）+ `run_agent_pipeline` Celery 任务 + `POST /api/agent/generate` 接口。
- GenerateAgent 复用现有 `run_generation`（创建任务 + delay + 轮询），不重复生成逻辑。
- 验证：提交「帮我画一只在太空的柯基」→ 224s 完成三步（优化提示词 → 出图 task_id=4 → 审图评价）。
- 踩坑：worker 容器需挂载代码 volume + LLM 环境变量（否则改 tasks.py 不生效、调 LLM 连不上）。

**后续**：升级为 LLM 自主决策（ReAct / function calling）；引入更多 Agent（修图、文案、多角色协作）。

### 3.2 Harness 评测引擎

- **选型决策**：自研轻量脚手架（数据集 + 指标 + 报告），LLM-as-Judge 打分。
- 评测 Agent 输出质量，做回归（改模型/提示词后自动跑）。

### 3.3 OpenCodeReview

- AI 代码审查：专门审查代码的 Agent + 审查规则。
- 复用阶段 1 的本地 LLM 与多 Agent 调度能力。

## 阶段 4：前端升级（Vue3 + Vite）

- **选型决策**：Vue3 + Vite + 组件库（Naive UI 或 Element Plus）。
- **理由**：响应式状态管理、组件化复用、HMR 热更新、组件库开箱即美化、工程化能力强。
- **迁移策略**：不推倒重来，按「登录+生图 → 图库 → 对话」分模块渐进迁移。
- 后端已 RESTful 化，前端用 axios/fetch 对接无缝。
- **待办：流式输出**（2026-09-24 决策延后至此阶段一起做）：
  - 对话助手改流式：模型 `stream:true` → 后端 SSE → 前端逐字渲染。
  - 动机：本地 Qwen3-VL 生成慢（约 5 token/s），非流式会导致长时间空白等待。
  - 后端：`llm_client.py` 加流式版本 + `chat.py` 改 SSE；前端：`sendChat` 用 ReadableStream 逐字渲染。
  - 需处理「流式 + RAG / 多模态 / 自定义模型」的兼容。
