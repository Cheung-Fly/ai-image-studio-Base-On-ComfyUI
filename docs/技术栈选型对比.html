选型总原则（四条）：① 就业导向——招聘 JD 出现频率高的技术优先；② 与 AI 生态同构——ComfyUI/PyTorch 都是 Python，全栈一种语言；③ 成熟 > 新潮——资料多、坑能搜到；④ 可平滑演进——SQLite→PostgreSQL、Redis→RabbitMQ、单机→Docker，代码不大改。

二、编程语言：Python 3.13

候选AI/生图生态后端队列生态上手成本结论
Python 选用统治级：ComfyUI、PyTorch、diffusers 全是 PythonFastAPI、Celery 成熟低与引擎同语言，可直接读 ComfyUI 源码、写自定义节点
Node.js / TS弱 推理侧几乎无生态Nest/BullMQ 不错中做前端 BFF 可以，做 GPU 调度要跨语言调 Python 服务，多一层
Java / Go弱很强（Spring/Go 并发）高/中大厂平台侧用得到，但个人 AIGC 项目开发慢、离模型远
选 Python 的决定性理由：生成引擎本身就是 Python 程序。后端、worker、（未来的）自定义节点共用一种语言和一套数据格式，调试链路最短。

三、Web 框架：FastAPI

候选异步参数校验自动 API 文档体量AI 岗位热度
FastAPI 选用原生 ASGIPydantic 自动白送 Swagger轻极高
Flask需拼手写/第三方flask-restx极轻高（偏老项目）
Django + DRF3.1 后支持serializer有重中
Spring Boot (Java)WebFluxBean Validationspringdoc很重传统后端高，AI 侧低
Express / Nest (Node)是需配 zod 等需配轻/中前端全栈方向
为什么是 FastAPI：① 一个 Pydantic 模型同时搞定"请求校验 + 422 错误 + OpenAPI schema + Swagger UI"，本项目的 /docs 零手写；② 类型注解即文档，简历上"FastAPI + 类型驱动开发"是 AIGC 应用岗高频要求；③ 异步底子好，未来接 WebSocket 实时进度顺理成章。
Flask 为什么不选：什么都要自己拼（校验、序列化、文档、异步），小项目看似轻，做到本项目这个规模反而要造一堆轮子。Django 为什么不选：自带的 admin、auth、模板、Django ORM 全用不上，却要接受它的目录约定和同步包袱。

四、ASGI 服务器：Uvicorn

候选协议角色结论
Uvicorn 选用ASGI（异步）单进程服务器，自带 --reloadFastAPI 官方标配，开发期直接用
GunicornWSGI（同步）为主多进程进程管理器生产上常用 gunicorn -k uvicorn.workers.UvicornWorker 管理多个 uvicorn 进程；开发期不需要
Hypercorn / DaphneASGI同类服务器能用但社区资料少，HTTP/2 等特性本项目用不上
原理上分清两层：FastAPI 是"应用"（不监听端口），Uvicorn 才是真正绑定 8000 端口、收发 HTTP 的服务器，它把网络请求翻译成 ASGI 规范交给 FastAPI。

五、任务队列：Celery（本项目最关键的选型）

候选成熟度/生态失败重试定时任务监控Windows 友好度结论
Celery 选用Python 事实标准自动重试/退避celery beatFlower需 --pool=solo功能最全、JD 高频，本项目重试/状态/队列都要
RQ轻量流行基础重试弱（rq-scheduler）rq-dashboard好极简任务够用，复杂编排（链/组/定时）吃力
Dramatiq / ARQ设计现代有有限弱一般技术不错但生态小、简历辨识度低
自研（Redis list + 线程）—全自己写无无—消息确认、崩溃恢复、重试、序列化都是坑，面试减分项
Kafka / RabbitMQ 裸客户端强自己实现消费者框架—那是"消息中间件"不是"任务队列"，缺 task 抽象
为什么是 Celery：它给的是一整套"分布式任务"抽象——@task 装饰器、.delay() 投递、worker 进程池、自动重试（本项目 max_retries=2）、状态追踪、定时任务、任务链/组、Flower 监控。这些正是生图平台（长任务、失败重试、批量、定时清理）的刚需，自己写任何一项都不便宜，且是面试官最爱深挖的部分。
Windows 的 pool 怎么选：默认 prefork 依赖 fork()（Linux 系统调用，Windows 没有）→ 本机用 --pool=solo（单线程串行，匹配 8GB 显存）或 --pool=threads；Linux 生产用默认 prefork 即可，无需改代码。

六、消息代理 Broker：Redis

候选定位可靠性/路由安装运维一专多能结论
Redis 选用内存键值库 / 轻量队列够用Windows 一键跑broker+结果后端+缓存+限流本机/中小规模最佳，Celery 改一行配置可换
RabbitMQ专业消息代理 AMQP最强：ACK、死信、路由偏重只做消息生产高可靠场景的升级目标
Kafka分布式日志流吞吐极高重（ZK/KRaft）不适合任务队列适合日志/事件流、大数据，生图任务队列是杀鸡用牛刀
数据库表当队列轮询一张 tasks 表依赖事务零新组件—极简 demo 可以；轮询有延迟、高并发锁表，不专业
为什么先用 Redis：一个组件同时当 broker 和 result backend，本机零负担，学习曲线最平。Celery 把 broker 差异封装在配置里，将来上线换 RabbitMQ 只改 REDIS_URL 一行，业务代码零改动——这就是队列抽象层的价值。

七、数据层：SQLAlchemy 2 + SQLite（开发）→ PostgreSQL（生产）

ORM 对比

候选评价
SQLAlchemy 2 选用Python ORM 事实标准，功能最全，方言支持 PG/MySQL/SQLite，2.0 支持现代类型注解写法
Django ORM好用但与 Django 框架绑定，不能单独拿来配 FastAPI
Tortoise ORM异步原生，但生态小、迁移工具弱、岗位辨识度低
原生 sqlite3 / SQL零抽象，但换数据库、防注入、关系查询都要自己扛

数据库对比

候选评价
SQLite 开发选用单文件、零安装、零服务，随项目拷走；通过 ORM 与生产隔离差异
PostgreSQL生产首选：并发写强、JSONB、全文检索、扩展多；AI 公司最常见
MySQL同样可行、运维普及度高；本项目无强偏好，PG 在 AI/海外团队更常见
关键设计：图片二进制不入库，数据库只存路径（images 表），文件放 data/images/。数据库存大二进制会膨胀、备份慢；文件系统 + 路径索引是图库类应用的标准做法（将来可平滑换成对象存储 S3/OSS，只改存取那一层）。

八、生成引擎：ComfyUI API 模式（项目核心，对比最该讲透）

候选工作流能力模型/LoRA/ControlNet 生态工程化/API学习与简历价值成本
ComfyUI 选用节点图，任意拼装最全、新模型首发支持原生 API：/prompt /history /view岗位核心技能本机显卡，0 元
diffusers 手写推理代码即流程要自己跟模型迭代直接函数调用偏算法研究0 元
A1111 / Forge API参数表单式插件多有 API 但工作流表达弱中0 元
商业 API（Replicate/闭源大模型）黑盒平台提供什么用什么HTTP 简单学不到引擎集成按张付费、数据出域
为什么是 ComfyUI：① 工作流即 JSON——画布导出 API 格式后，参数化（{{prompt}} 占位符注入）就能做成产品模板，换模型/换采样器只改 JSON 不改代码；② 新模型（你机器上的 Krea2、MiniMax）生态跟进最快，LoRA/ControlNet/图生图/视频统一是"加节点"；③ 自带队列和 output 管理，后端只需"提交—轮询—取图"三个接口；④ 招聘 JD 里"ComfyUI 工作流产品化"正是这个项目的定位。
diffusers 什么时候选：做模型微调、算法研究、需要把推理嵌进训练 pipeline 时。它比 ComfyUI 灵活但工程化要全自己写（模型加载调度、显存管理、节点依赖、队列），对应用开发岗性价比低。商业 API 什么时候选：验证产品创意、不持有 GPU、追求上线速度时；但它让项目退化成"普通 CRUD 调第三方"，就业竞争力和可控性都打折。

九、HTTP 客户端：httpx

候选同步/异步HTTP/2与测试集成结论
httpx 选用同步+异步同一套 API支持FastAPI TestClient 底层就是它现在同步写 worker，未来改异步零迁移成本
requests仅同步不支持—最经典但项目维护模式化、异步时代的上一代选择
aiohttp仅异步支持—偏底层，仅异步，写同步脚本不方便

十、前端：Vue 3 + Vite + Pinia（第 2 周里程碑）

候选定位像不像"产品"上手成本结论
Vue 3 + Vite + Pinia 选用主流 SPA 框架完整前端工程中模板语法直观、中文生态强、Vite 秒级热更新；Pinot 是 Vue 官方状态库
React + Vite主流 SPA 框架是中高（JSX/hooks）岗位更多但概念更碎；两个都会更好，先 Vue 快速出活
Gradio / StreamlitAI 演示框架像 demo 不像产品极低算法演示神器，但没有队列/图库/工程化展示，撑不起"全栈平台"简历叙事
就业项目要证明的是"能把模型包成产品"：提示词面板、参数表单、任务进度轮询、图库管理——这是标准前端工程，Vue 正好覆盖这些训练点。

十一、环境、测试与部署工具

虚拟环境 / 包管理

候选特点结论
venv + pip 选用Python 自带、零安装、概念最基础教学和入门项目最稳，面试官默认你懂
uv / Poetry / PDM锁文件、依赖解析、uv 速度极快进阶推荐：uv 是 2025 后行业趋势，熟练后可替换（命令几乎兼容）
conda / miniconda管 Python 版本 + 原生库（CUDA 等）数据科学/需要不同 Python 版本时用；纯 Web 项目偏重

测试：为什么用"内置假服务 + eager"而不是直接跑真链路

方式速度依赖 GPU/Redis结论
http.server 模拟 ComfyUI + Celery eager + TestClient 选用2 秒都不需要验证业务逻辑（路由/状态机/落盘/序列化），CI 友好
真实 ComfyUI + Redis 端到端分钟级全依赖发布前手动跑一次即可，不适合每次改代码都跑
测试替身（mock/stub）是工程岗必考概念：我们测的是"自己的业务代码对不对"，不是测 ComfyUI 会不会出图——后者是它的开发者要保证的。后续可升级为 pytest + respx（mock httpx），结构更标准。

部署：Docker Compose

候选特点结论
Docker Compose 进阶选用一个 yaml 声明 redis/api/worker 三个服务，一条命令起全套环境一致、可复现、简历加分；ComfyUI 留宿主机做 GPU 直通
裸机 + systemd/脚本手工装 Redis、配两个服务开机自启能跑但不可复制、换台机器重来一遍
Kubernetes容器编排集群本项目过重；多机多副本、自动扩缩容时才需要，是后期学习目标
