一句话理解分工：FastAPI 像"前台接单员"，Redis 像"工单传送带"，Celery worker 像"后厨"，ComfyUI 是"炉灶（GPU）"，SQLite 是"订单台账"，文件夹是"取餐柜"。前台绝不站在炉灶前等菜做完——接单、派单后立刻回去接待下一位客人。

二、为什么非要拆成 API + 队列 + Worker？

出一张图要 30 秒～3 分钟（首次还要加载 13GB 模型）。如果让 HTTP 请求在 FastAPI 里同步调用 ComfyUI 并死等结果，会有四个硬伤：

问题后果队列架构如何解决
请求长时间挂起浏览器/网关一般 30～60 秒超时，页面转圈失败API 入库+发消息后立即返回 202 和 task_id（毫秒级）
并发请求堆积10 个人同时点，10 个出图任务一起挤进 8GB 显存，直接 OOM任务在 Redis 排队，worker 按 --pool=solo 串行处理，削峰填谷
失败无法恢复出图中途网络抖动，整个请求白等，只能用户手动重来Celery 内置重试（本项目连接类失败自动重试 2 次）、状态可追踪
API 重启任务全丢正在等的请求随进程一起消失任务持久在 Redis + 状态在 SQLite，worker 重启后可继续/可查

这就是经典的 生产者—消费者模式：API 是生产者，worker 是消费者，两者解耦，各自独立启停、独立扩容（以后量大了可以多开几台 worker 机器）。这也是岗位面试中"AIGC 应用工程化"的高频考点。

三、逐步讲解：每条命令背后的原理

前置Redis 与 ComfyUI 为什么要先开着

Redis 是一个内存型键值数据库，在这里充当 Celery 的 消息代理（broker）：worker 启动时会连接 6379 并"订阅"一个名为 aistudio 的队列；API 投递任务时，Celery 把 {"任务名":"app.workers.tasks.run_generation","参数":[任务id]} 序列化成 JSON 推进 Redis 的列表（底层相当于 LPUSH/BRPOP）。worker 阻塞等待、取到即执行。它还兼任 result backend（存任务返回值），但本项目的业务状态主要落在 SQLite。
ComfyUI 是真正驱动 GPU 出图的服务。本项目的后端自己不含任何 AI 模型代码，只是它的 HTTP 客户端——所以必须先有 ComfyUI 在 8188 端口待命。

第 1 步创建虚拟环境 + pip install -r requirements.txt

venv 原理：在 backend/.venv 里放一套独立的 Python 解释器链接和独立的 site-packages 包目录。激活（Activate.ps1）后，终端的 PATH 优先指向它，于是 python 和 pip 都只作用于这个项目——不同项目可以用不同版本的包，互不污染，也不动系统 Python。

安装的包在项目里扮演什么角色
uvicorn[standard]ASGI 服务器：真正监听 8000 端口、收发 TCP/HTTP 的程序；把请求按 ASGI 规范交给 FastAPI。--reload 是开发期文件改动自动重启。
fastapiWeb 框架：URL 路由、Pydantic 参数校验、依赖注入、JSON 序列化、自动生成 /docs。
sqlalchemyORM：用 Python 类/对象操作数据库，自动生成 SQL，不手写 sqlite3。
pydantic / pydantic-settings请求体的类型与取值范围校验（不合格自动返回 422）；从环境变量读取配置。
celery分布式任务队列框架：提供 @celery_app.task、.delay()、worker 命令行、重试机制。
redisRedis 的 Python 客户端，Celery 用它连接 broker。
httpxHTTP 客户端，worker 用它调用 ComfyUI 的三个接口；冒烟测试也用它的 TestClient 打 API。
pillow读取下载回来的图片宽高，写入 images 表。

第 2 步冒烟测试 python tests\smoke_test.py —— 它是怎么"无中生有"跑通的？

这一步不需要 Redis、不需要 ComfyUI、不起真实端口，却能把整条业务链路测一遍，靠两个"替身"：

替身 1：假的 ComfyUI 服务
测试脚本在本机随机端口起一个极简 HTTP 服务（ThreadingHTTPServer），按 ComfyUI 的接口契约返回固定内容：
  • POST /prompt → 回一个固定 prompt_id
  • GET /history/<id> → 回"已完成"+一张图片的文件名
  • GET /view → 回一张 1×1 像素的合法 PNG
替身 2：Celery eager 模式
设置 task_always_eager=True 后，.delay() 不再往 Redis 发消息，而是在当前线程里立刻同步执行任务函数。于是不需要 worker 进程，API 调用走完时图也"生成"完了。

再配合 FastAPI 的 TestClient（进程内直接调用应用，不起网络端口）和临时目录（数据库、图片都写进系统临时文件夹），8 个断言依次验证：健康检查 → 接单返回 202 → 任务 completed → 详情带图 → 图库非空 → 下载是合法 PNG → 状态过滤 → 不存在返回 404 → 工作流参数注入正确。

价值：改完代码 2 秒自检，不依赖显卡环境；以后接 CI/CD，每次提交自动跑。这是工程化项目的"安全网"。

第 3 步启动 API：uvicorn app.main:app --port 8000

app.main:app 的含义是"从 app/main.py 里导入名为 app 的 FastAPI 实例"。启动时发生：
① uvicorn 绑定 8000 端口开始监听；② 触发 lifespan，调用 init_db() 在 SQLite 里建好 tasks/images 两张表；③ 注册三个路由模块（generate / tasks / images）；④ 根据代码里的类型注解自动生成 OpenAPI 文档，所以 /docs 的 Swagger 页面是"白送"的。
一次请求进来后：路由函数接收 → Pydantic 把 JSON 校验为 GenerateRequest（width 超出 256~2048 直接 422）→ get_db() 依赖注入给一个数据库会话，请求结束自动关闭 → 业务处理 → response_model 把 ORM 对象转成 JSON 返回。

第 4 步启动 Worker：celery -A app.workers.celery_app worker --pool=solo

-A app.workers.celery_app 指定 Celery 应用实例所在模块；worker 启动后连上 Redis、注册 include 里声明的任务函数，然后进入死循环等消息。看到 celery@... ready. 就是就绪。
为什么 Windows 必须加 --pool=solo？Celery 默认的 prefork 池用操作系统的 fork() 创建子进程来并发执行任务，而 Windows 没有 fork，直接报错；solo 是单线程池（一次一个任务，正好匹配 8GB 显存串行出图），想用并发可换 --pool=threads --concurrency=2。
Worker 和 API 是两个完全独立的进程，靠 Redis 里的消息和共享的 SQLite 文件协作——所以必须各开一个终端，缺一不可。

第 5、6 步提交任务 & 查看结果 —— 完整链路时序

FastAPI：收到 POST /api/generate，Pydantic 校验 prompt/尺寸/steps 等参数。
原理：非法参数在进业务逻辑前就被拦下，返回 422。
FastAPI：在 tasks 表插入一行，status=pending，commit 后拿到自增主键 task_id。
先落库再派单：任何任务都有据可查，不依赖内存。
FastAPI → Redis：调用 run_generation.delay(task.id)，Celery 把任务消息序列化后推进 Redis 队列。
这一步只是"塞工单"，不做出图。
FastAPI：立即返回 202 Accepted + 任务对象（此时还是 pending）。
HTTP 请求在几十毫秒内结束，不会超时。
Celery Worker：从 Redis 取到消息，把状态改为 processing。
状态机推进；前端轮询 /api/tasks/{id} 就能看到变化。
Worker · workflow.py：读取 workflows/txt2img_api.json 模板，把 {{prompt}}、{{width}}、{{steps}}、{{seed}} 等占位符替换成实际参数。
模板与代码分离：换模型/调节点只改 JSON，不动 Python。
Worker → ComfyUI：POST http://127.0.0.1:8188/prompt，body 是 {"prompt": 工作流JSON}；ComfyUI 校验节点、排队执行，返回 prompt_id 存库。
ComfyUI 自己也有队列，GPU 任务在它那边串行跑。
Worker ↔ ComfyUI：每 2 秒 GET /history/{prompt_id} 轮询，直到状态 completed 且 outputs 里出现 SaveImage 节点产出的图片文件名。
轮询是最简单可靠的进度同步方式（后续里程碑可升级 WebSocket）。
Worker ← ComfyUI：用 GET /view?filename=...&type=output 把 PNG 字节下载回来，存到 data/images/{task_id}/，Pillow 读宽高，在 images 表插记录。
平台自己留存一份，不依赖 ComfyUI 的 output 目录，便于图库管理。
Worker：把任务状态改为 completed；任何环节异常则改为 failed 并记录 error，连接类瞬时错误自动重试最多 2 次。
你调 GET /api/tasks/1 看到 completed 和图片 URL，全链路闭环。

五、ComfyUI API 模式与工作流模板注入

平时你在 ComfyUI 网页里拖节点连线；开启 API 模式后，画布可以导出成一份 JSON：key 是节点编号，value 是 {"class_type": 节点类型, "inputs": 参数}；inputs 里形如 ["1", 0] 的数组表示"接 1 号节点的第 0 个输出口"——这就是连线。本机没有传统 SD checkpoint，模板已按 Krea 2 组合模型配好，节点链如下：

六、数据落在哪里：两张表 + 一个文件夹

存储内容为什么这么设计
SQLite：tasks 表提示词、负向词、宽高、steps、cfg、seed、status、error、comfy_prompt_id、创建/更新时间任务台账：支持列表分页、状态过滤、失败排查
SQLite：images 表所属 task_id（外键）、磁盘文件名/相对路径、宽高图库：一个任务可对应多张图（以后支持 batch）
文件夹 data/images/<id>/真实 PNG 文件数据库只存路径，二进制不入库；/api/images/{id}/file 用 FileResponse 回传

SQLite 是嵌入式文件数据库，无需独立安装服务，适合本机开发；将来上生产只需把 DATABASE_URL 换成 PostgreSQL 连接串，ORM 代码基本不动——这就是数据访问层抽象的意义。

八、30 秒串讲（可以直接讲给面试官）

"这是一个把 ComfyUI 工作流产品化的 AIGC 生图平台。前端提交提示词和参数到 FastAPI，API 用 Pydantic 校验后把任务写入 SQLite（状态 pending），并通过 Celery 向 Redis 队列投递消息，立即返回任务 ID。Celery worker 异步消费任务，把参数注入参数化的 ComfyUI 工作流模板，调用 ComfyUI 的 /prompt 接口提交、轮询 /history 等待完成、再经 /view 下载图片落盘并回写状态为 completed，全程是 pending→processing→completed/failed 的状态机，失败可重试。我还写了基于模拟服务和 Celery eager 模式的端到端冒烟测试，不依赖 GPU 即可验证全链路。下一步是 Vue 前端、WebSocket 实时进度和 Docker 编排。"
